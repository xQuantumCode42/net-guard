# NetGuard 跨平台個人網路防護工具設計

日期：2026-11-21

狀態：設計草案，待使用者確認；尚未實作或驗證相容性。

## 1. 目的與已確認需求

開發具桌面介面的個人安全工具，涵蓋 Windows、macOS、Linux 上的對外連線，包括背景服務、下載工具、更新程式與瀏覽器。使用者能了解哪些程式正在連網，並依規則阻擋不受信任的目的地。

使用者已確認：

- 先供個人使用。
- 共用邏輯優先使用 Rust；必須有桌面 UI。
- 三平台皆為正式目標，不以只有 Windows 的版本宣稱完成。
- macOS 以最新版為支援目標；Linux 首批支援 Ubuntu 與 Arch Linux，其他發行版日後擴充。
- 採原生攔截方案。
- 支援自動或手動啟動、惡意目的地封鎖及詢問模式。
- 可新增、刪除黑白名單，並可匯入現成威脅資料。
- 第一版監控程式、IP、連接埠、協定及可取得的網域，不解密 HTTPS 路徑或內容。
- 產品為通用工具，不綁定特定防毒、防火牆或 VPN 品牌；使用者現有軟體只是開發測試案例。

以下明確標為「建議」的細節是設計者提案，不代表使用者已逐項同意。

## 2. 範圍與保護邊界

### 第一版目標

- 觀察並控制支援之主機網路路徑上的對外連線，包含 IPv4、IPv6、TCP、UDP／QUIC；另驗證 ICMP 與 DNS。
- 顯示來源程式、目的 IP／連接埠、協定、時間、判斷結果與命中規則。程序歸屬或網域不可取得時必須明示未知。
- 上下載量作為盡力提供的統計，顯示統計範圍與是否可用；連線事件不等於封包計量。
- 規則於可用的連線授權或封包處理點執行，不以週期性列出連線再終止來假冒連線前封鎖。
- UI 關閉不停止已啟用的服務；提供明確的暫停與恢復防護操作。
- 本機判斷為主，名單更新可連網；不為每次連線向外部服務上傳使用者目的地。

### 不承諾與不納入第一版

- 黑名單不等於完整資料外洩防護；未收錄目的地、正常雲端服務被濫用等仍可能漏過。
- 不做 TLS 中間人解密、不安裝攔截用根憑證、不掃描下載內容、不提供遠端 VPN 服務。
- 不保證每條連線都有唯一網域、完整 URL 或可靠程序身分。
- 已有 VPN、代理、容器、虛擬機及特殊核心網路路徑可能改變可見性。第一版不宣稱覆蓋所有此類流量；必須以能力狀態及測試紀錄說明。
- 第一版不宣稱能防禦已取得核心或系統管理權限的攻擊者。
- 開機自啟不等於從開機第一個封包起即有保護；第一版以服務與攔截器就緒後開始計算防護覆蓋。

## 3. 方案比較與選擇

| 方案 | 優點 | 代價與限制 | 決策 |
| --- | --- | --- | --- |
| 原生攔截加 DNS 資訊整合 | 在系統支援的層次作連線決策，可整合程式身分，無須為攔截另接管所有路由 | 各平台需獨立整合、簽章及實測 | 使用者已選擇 |
| 本機 VPN／虛擬網卡 | 封包處理邏輯較集中 | 轉送、路由、程序歸屬、既有 VPN 與 DNS 協調成本較高 | 不作第一版架構 |
| 僅 DNS 過濾 | 網域規則容易開始 | 無法單獨涵蓋直接 IP、繞過系統 DNS 的流量 | 不足以滿足需求 |

## 4. 建議技術與模組邊界

- 桌面介面：Tauri 2、TypeScript、React；共用三平台的操作流程。
- Rust 規則核心：規則正規化、匹配、優先序、名單解析、期限及決策原因。
- Rust 背景服務：管理平台攔截器、事件、規則快照、更新與健康狀態。
- SQLite：保存使用者設定、規則、名單版本、例外及有限期事件。
- 原生橋接：Windows 必要的 WFP／WDK 程式碼、macOS Swift Network Extension；不要求所有系統整合都使用 Rust。
- 攔截快速路徑使用經驗證的記憶體規則快照，不對每個封包查 SQLite、等待 UI 或查遠端 API。
- UI 使用一般使用者權限；只有必需的服務與攔截模組取得系統權限。
- Windows 透過受 ACL 保護的 named pipe、Unix 平台透過受權限保護的 socket 或平台適用的 XPC 通訊；驗證對端身分與可執行操作，不開放無驗證的本機 HTTP 控制埠。
- 桌面前端只載入本機介面，採最少 Tauri capabilities；不讓網頁取得任意命令執行能力。

預計程式結構可分為 desktop、core、service、platform/windows、platform/macos、platform/linux；精確 workspace 結構留給實作計畫。

## 5. 三平台攔截策略

### Windows

- 使用 WFP 的合適 ALE 授權層控制 TCP 與 UDP 等連線，處理 IPv4／IPv6。
- 區分可由既有 WFP filter 表達的規則與需 callout driver 的動態分類。
- 若動態程序規則、阻擋事件或未知連線處理需要 callout，先驗證最小驅動及服務通訊；不能把列舉連線或事後日誌視為替代品。
- 設計採阻擋後詢問與重試，不把長時間 pending 連線作為通用互動保證。
- 計量、程序生命週期及 PID 重用另外處理，不假定 ALE 連線事件可直接得出位元組數。
- 測試驅動只在適當的隔離開發環境驗證；一般使用者安裝需要符合 Windows 發佈簽章要求，不以關閉系統保護作正式安裝步驟。

### macOS

- 以驗收當時 Apple 最新正式版 macOS 為首批目標，記錄完整版本與 build；「最新」預設不含 beta／開發者預覽版。移除原先 macOS 14 以上的廣泛相容性提案。
- 新正式版本推出後需重新執行安裝、擴充授權、攔截及共存測試，再更新已驗證支援表，不直接把尚未驗證的版本標為相容。
- 使用 Network Extension content filter／必要的 packet filter 與 System Extension 部署方式。
- Swift 原生擴充與 Rust 核心間採平台允許的資料交換方式；先驗證 sandbox、共享規則、事件回報與內容存取限制。
- 驗證 entitlement、Developer ID 簽章、公證、啟用授權以及擴充／主程式更新流程。
- 不以修改非公開封包過濾介面或關閉系統完整性保護作正式方案。

### Linux

- 使用獨立 nftables table／chain 與 sets，不能清除或覆寫其他軟體管理的規則。
- 需要動態判斷時採 NFQUEUE，驗證 queue 滿載、listener 消失及封包重新進入 queue 的處理。
- 程序身分不是 NFQUEUE 封包自帶的可靠欄位；先驗證 socket／cgroup／必要的 eBPF 輔助方案。無法可靠歸屬時標示未知，不只用事後掃描 `/proc` 宣稱精確。
- 首批正式目標為 Ubuntu 與 Arch Linux，其他發行版不列入第一版完成條件，日後擴充。
- Ubuntu 建議先以最新 LTS 的最新維護版本、x86_64、systemd、nftables 為驗證基準；截至 2026-11-21 官方列出的最新 LTS 系列為 26.04。採 LTS 是設計者建議，使用者尚未指定 Ubuntu 版本。
- Arch Linux 採官方穩定套件庫、完整更新的 x86_64 系統作基準，不使用 testing 套件庫。記錄測試日期、核心、nftables、systemd、WebKitGTK 與套件版本，以對應其滾動更新模式。
- Ubuntu 與 Arch 分別驗證安裝／升級／移除、服務、自啟、依賴及桌面整合；共用 Linux 攔截邏輯不代表可省略各發行版測試。建議提供 Ubuntu 的 .deb 與 Arch 的 PKGBUILD／可安裝套件，不以僅能啟動 UI 的便攜包代表服務已安裝。
- 首批桌面環境與 Wayland／X11 組合由實作計畫明列，不宣稱所有桌面環境皆已測通。

### 發佈與驗證界線

使用者已確認的平台範圍為 Windows、最新 macOS，以及 Ubuntu／Arch Linux。建議首批 CPU／版本基準為 Windows 11 x64、最新正式版 macOS 的 Apple Silicon、Ubuntu 最新 LTS x86_64、Arch Linux 穩定套件庫 x86_64；CPU 架構與 Ubuntu 採 LTS 仍屬設計者提案。上述是支援目標，不是已測通的平台；其他 CPU 架構、舊版本與其他 Linux 發行版另行擴充。共同程式碼可共用，但三平台及兩個 Linux 發行版需分別建置、安裝及實機測試，並完成各平台適用的簽章。實作前需確認 macOS 建置環境與開發者簽章資源，以及 Windows 驅動發佈資源。

## 6. 規則與互動語意

### 模式（建議）

- 一般模式：命中有效阻擋規則即阻擋，其餘放行並依設定記錄。
- 詢問模式：命中需要使用者決定的規則時先阻擋，再通知。
- 嚴格模式為後續可開啟選項：未被允許的程式／目的地組合先阻擋並詢問；不預設對所有使用者啟用。
- 使用者允許後只影響後續連線，原程式需要重試；DNS 負快取也可能延後恢復，不承諾原連線立即續接。
- UI 未開、尚未登入或使用者未回應時，需要詢問的事件維持阻擋。通知去重、限速並保留可查詢紀錄。
- 建議允許操作提供 10 分鐘與永久兩種，不在第一版提供跨協定語意不明的「只允許一次」。

### 規則表示

- 支援單一 IP、IPv4／IPv6 CIDR、精確網域、明確指定的子網域範圍；可附加程式、協定與連接埠限制。
- 程式規則使用平台可取得的身分資料；不能以可重用 PID 作永久身分，也不承諾路徑規則能抵禦本機高權限替換。
- `example.com` 與「包含其子網域」分開設定，使用 DNS 標籤邊界匹配，避免誤中 `notexample.com`。
- 網域正規化處理大小寫、尾點與 IDNA；地址處理 IPv4／IPv6 格式與 CIDR 合法性。
- 訂閱資料保留來源、指標類型、有效期與觀察時間。URL 指標不直接轉成整個共用 IP 的封鎖。

### 建議優先序

1. 使用者規則依顯式順序評估，第一個命中規則決定動作；UI 支援排序並顯示衝突。使用者不必推測同時命中黑白名單時哪個生效。
2. 指定來源／指標的訂閱例外，僅略過該訂閱項目。
3. 有效且啟用的訂閱阻擋規則。
4. 目前模式的預設動作。

短期允許也是有期限、可見的使用者規則，插入後顯示其優先序。允許某網域不自動建立共用 IP 的全面白名單。資料不足時不能讓網域白名單匹配未知連線。

刪除自己建立的規則是真正刪除；對訂閱項目選擇移除，保存持久的訂閱例外，避免下一次更新重新加入。UI 說明兩者差異。

## 7. DNS 與網域可見性

- 第一階段以支援的系統 DNS 事件、可用平台資訊與經驗證的關聯建立網域資料，區分直接證據與推測關聯。
- DNS 回覆與 IP 的映射保留 TTL、來源範圍及時間；共用 IP 或模糊關聯不作唯一網域證據。
- 本機 DNS 過濾器可作選用模組，先驗證上游、VPN split DNS、網路切換與復原，不能預設搶占 DNS 設定。
- 應用程式內建 DoH／DoT、ECH 或代理可能導致網域未知；不假裝完整攔截，也不為取得網域自動降低加密保護。
- 模組未啟用或有盲區時，UI 分開顯示「IP 防護可用」與「網域防護範圍」。
- 網域封鎖的驗收要涵蓋 DNS 可見路徑；對不可見路徑驗證未知顯示與 IP／程式規則仍可用。

## 8. 威脅資料與更新

- 初始建議以 Spamhaus DROP 的 IP 網段資料作第一個匯入器，遵守其條款、歸屬與更新要求。
- URLhaus、ThreatFox 作個人使用的選配來源；使用者提供自己的 Auth-Key，並依當時 API 與使用條款下載。
- 不把需個人憑證或不確定再散布權限的資料／金鑰打包進安裝程式。
- 預設快照只有在可再散布條款核對完成後才隨安裝包提供，保存日期與來源。否則首次連網下載，UI 明示尚未載入預設資料。
- 網域指標只選用可合理整個網域封鎖的來源與格式；完整 URL 不直接降級成網域封鎖。
- 更新依來源頻率限制進行，採退避、下載大小限制、結構驗證及原子替換；失敗保留上一份有效資料。
- 過期指標不永久累積封鎖；過期及更新失敗須顯示。可保留歷史版本供診斷與回復。
- API 金鑰存放 OS credential store，日誌與 URL 記錄遮蔽金鑰。

## 9. 與其他安全軟體及 VPN 共存

- 不綁定任何供應商，不要求使用者安裝特定防毒或 VPN。
- 不自動停用既有防毒、防火牆、VPN Kill Switch 或其他保護；不以新增廣泛白名單作預設修復。
- 本工具的允許只代表自身規則允許，不能覆寫其他安全軟體的拒絕。無法判定外部阻擋原因時不可冒稱已定位。
- 不改變既有 VPN 的路由、分流與 DNS，除非使用者日後明確啟用需修改設定的功能。
- 分別驗證一般網路、完整隧道、分流、VPN 斷線／重連、Kill Switch、DNS 改變與睡眠恢復。
- 驗證加密前的應用連線及隧道外層連線是否被重複計量；如只能看見 VPN 端點，清楚顯示可見性限制。
- 不因識別出 VPN 程式就全面放行其所有流量，避免成為繞過規則的捷徑。
- 相容性報告按平台、產品版本、啟用功能與測試日期記錄；不得由單一案例推論所有產品相容。

## 10. 啟動、異常與移除（建議）

- 啟動方式與防護模式為兩組設定；以 Windows service、launchd／System Extension、systemd 實作各平台所需生命週期。
- 開機服務與登入後 UI 分開；服務達到可攔截狀態後才顯示防護啟用。
- 畫面區分正常、部分可見、服務失效、等待授權、未載入名單，不以單一綠燈掩蓋盲區。
- 初版建議服務異常採恢復網路可用性的策略（fail-open），但不同後端規則可能持續生效；必須以 watchdog／租約與復原機制驗證一致語意，不能只寫設定卻不實現。
- 正常運作時等待使用者決策仍採先阻擋；與服務故障時的策略分開。
- 尚未驗證的故障恢復路徑是發佈阻擋項；嚴格 fail-closed 為未來選項，第一版不宣稱提供。
- 規則更新採版本化快照與可回復替換；停止或解除安裝只移除本工具擁有的規則、服務與擴充，不重設整台電腦的網路。

## 11. 桌面 UI 功能範圍

- 防護狀態：各平台模組、服務、名單、網域可見性的狀態與原因。
- 連線活動：按程式、目的地、時間與結果篩選；顯示未知欄位與可用的上下載統計。
- 規則管理：黑白名單增刪、順序、作用範圍、到期時間、訂閱例外、匯入匯出。
- 阻擋事件：命中原因、來源、短期／永久允許、維持阻擋，避免直接開啟可疑網址。
- 設定：自啟、模式、通知、日誌保存、更新與復原。
- 建議事件紀錄預設保留 7 天且設 100 MB 上限，達上限輪替；可停用、清除或手動匯出。預設不保存封包內容、不上傳遙測。

## 12. 分階段驗證與完成條件

### 階段 A：三平台可行性

各平台先完成最小攔截驗證：背景測試程式建立連線、命中規則、受控伺服器確認未收到被阻擋的應用資料；另外驗證程序歸屬、事件與權限。這不是只完成 Windows 就結案。先驗證風險最高的簽章／擴充／程序識別，再擴大 UI。

### 階段 B：共用核心與操作閉環

驗證規則優先序、正規化、期限、匯入與更新回復；完成阻擋、通知、使用者允許、程式重試、撤銷規則的閉環。測試使用受控端點或測試網域，不需連線真實惡意網站。

### 階段 C：跨平台與共存驗收

- 三平台的安裝、啟動、權限、背景連線、IPv4／IPv6、TCP／UDP、DNS 與 QUIC。
- Linux 驗收分別覆蓋 Ubuntu 與 Arch Linux；macOS 記錄驗收時最新正式版的完整版本與 build，Arch 記錄當日套件與核心版本。任一首批目標未驗證都必須明示，不可由另一發行版的測試結果代替。
- 背景上傳與下載均要測，不以瀏覽器操作代替。
- 已存在連線於新增封鎖規則後的處置需明確：驗證可立即終止的路徑；不支援時明示只影響後續連線，不宣稱立即阻止既有資料流。
- 在遠端受控端點核對阻擋結果，區分「禁止應用資料」與「網路層連任何封包都未送出」。
- 至少驗證可取得的第三方防毒／防火牆／VPN 組合；現有個人環境只是一組案例。
- 斷線重連、睡眠恢復、介面切換、服務終止、queue 滿載、名單損壞、磁碟滿、UI 關閉及解除安裝。
- 對正常連線量測延遲、吞吐、CPU／記憶體與掉事件情況，以無工具時作基線。先訂可接受預算再調校，不宣稱零影響。

只有三平台的核心驗收完成，才能稱為三平台可用。單一環境編譯成功、模擬攔截器或純 UI 原型不能算作實際網路防護完成。

## 13. 留給實作計畫的決策

- 精確套件版本、Rust FFI 形式、Windows callout 最小範圍及 Linux 程序辨識實作。
- 平台事件與計量 API、批次傳輸策略、資料庫索引及容量調整。
- CI、安裝包格式、可重現建置、更新簽章與金鑰管理細節。
- 依可行性驗證結果調整最小 OS 版本；改動須保留三平台目標並說明功能差異。

需要在實作前確認的資源：三平台測試機或適用的 VM、macOS 簽章與建置資源、Windows 驅動簽章及隔離測試環境。資源尚未確認不代表可以將未測平台標為支援。
